# مدل داده‌ی Petal

**وضعیت: طرح توسط کاربر تأیید و در مرحله‌ی ۵ در SQLite پیاده‌سازی شده است.**

## هدف

این طرح، اطلاعات هر پروژه و تخته‌ی آن را در SQLite نگه می‌دارد و مالکیت هر پروژه را به کاربر نشست‌دار متصل می‌کند. قرارداد JSON در [`backend/schemas/kanban.schema.json`](../backend/schemas/kanban.schema.json) شکل یک تخته را مشخص می‌کند. این قرارداد، طرح جدول‌های SQLite نیست.

## روابط پیشنهادی

```text
users 1 ─── * projects 1 ─── * columns 1 ─── * cards
```

- هر پروژه دقیقاً یک تخته دارد؛ جدول جداگانه‌ی `boards` لازم نیست. تخته با مجموعه‌ی ستون‌های وابسته به پروژه نمایش داده می‌شود.
- `users`: شناسه‌ی پایدار و نام کاربری یکتا. حساب آزمایشی `user` یک ردیف ثابت خواهد داشت. رمز آزمایشی در این مدل داده ذخیره نمی‌شود؛ بررسی `user` / `password` همان رفتار آزمایشی سمت سرور مرحله‌ی ورود باقی می‌ماند.
- `projects`: نام پروژه، شناسه‌ی مالک و موقعیت پروژه در فهرست همان کاربر.
- `columns`: پروژه‌ی والد، نام ستون و موقعیت آن در تخته.
- `cards`: ستون والد، عنوان، جزئیات و موقعیت کارت در ستون.

## طرح رابطه‌ای پیشنهادی برای مرحله‌ی بک‌اند

| جدول | ستون‌ها و قیود پیشنهادی |
|---|---|
| `users` | `id TEXT PRIMARY KEY`, `username TEXT NOT NULL UNIQUE` |
| `projects` | `id TEXT PRIMARY KEY`, `user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE`, `name TEXT NOT NULL`, `position INTEGER NOT NULL CHECK(position >= 0)`, `UNIQUE(user_id, position)` |
| `columns` | `id TEXT PRIMARY KEY`, `project_id TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE`, `title TEXT NOT NULL`, `position INTEGER NOT NULL CHECK(position >= 0)`, `UNIQUE(project_id, position)` |
| `cards` | `id TEXT PRIMARY KEY`, `column_id TEXT NOT NULL REFERENCES columns(id) ON DELETE CASCADE`, `title TEXT NOT NULL`, `details TEXT NOT NULL DEFAULT ''`, `position INTEGER NOT NULL CHECK(position >= 0)`, `UNIQUE(column_id, position)` |

شناسه‌ها در SQLite از نوع `TEXT` هستند تا شناسه‌های فعلی مانند `project-board`، `todo` و `todo-1` قابل حفظ باشند؛ شناسه‌های تازه می‌توانند UUID باشند. یکتایی کلید اصلی در هر جدول شناسه‌ی تکراری همان موجودیت را رد می‌کند. مالکیت پروژه از `projects.user_id` می‌آید؛ تمام خواندن و نوشتن پروژه/تخته باید هم‌زمان به کاربر نشست‌دار محدود شود و به شناسه‌ی ارسالی درخواست اعتماد نکند.

حذف کاربر، پروژه یا ستون در طرح رابطه‌ای آبشاری است؛ قابلیت حذف پروژه/ستون در همین مرحله اضافه نمی‌شود. فعال‌کردن `PRAGMA foreign_keys = ON` برای هر اتصال SQLite لازم است.

## ترتیب و شکل JSON

- ترتیب پروژه‌ها، ستون‌ها و کارت‌ها در جدول‌ها با `position` عددیِ صفرمبنا ذخیره می‌شود؛ این شامل جابه‌جایی کارت‌ها درون همان ستون نیز هست.
- در JSON، ترتیب آرایه‌ی `columns` و آرایه‌ی `cards` همان ترتیب نمایش است؛ فیلد `position` در payload تکرار نمی‌شود.
- هر تخته حداقل پنج ستون دارد، چون رفتار محصول تخته را با پنج مرحله‌ی نمونه آغاز می‌کند و حذف ستون در محدوده‌ی فعلی نیست؛ افزودن ستون تعداد را افزایش می‌دهد.
- ساخت پروژه‌ی جدید پنج ستون پیش‌فرض و بدون کارت می‌سازد. پروژه‌ی نمونه‌ی اولیه می‌تواند کارت‌های نمایشی فعلی را نگه دارد.
- محدودیت پیشنهادی: نام پروژه و ستون حداکثر ۱۲۰ نویسه، عنوان کارت ۲۰۰ نویسه و جزئیات کارت ۵۰۰۰ نویسه. رابط و API باید در مرحله‌ی اتصال داده با این حدود سازگار شوند.
- شناسه‌ی کاربر و `user_id` در JSON تخته قرار نمی‌گیرد؛ سرور مالک را از نشست تعیین می‌کند.

## چرایی SQLite

- برای اجرای محلی تک‌کاربره، بدون سرویس جداگانه و با پشتیبانی تراکنش و کلید خارجی مناسب است.
- داده در یک فایل باقی می‌ماند و پس از restart حفظ می‌شود.
- در Docker Compose، فایل پایگاه‌داده در `/data/petal.db` و volume نام‌دار `petal-data` نگهداری می‌شود؛ در اجرای مستقیم بک‌اند، مسیر پیش‌فرض `backend/data/petal.db` است.
- هنگام جابه‌جایی یا مرتب‌سازی، تغییر موقعیت‌ها باید داخل یک تراکنش انجام شود تا قید یکتایی ترتیب نقض نشود.

## مرزهای این پیش‌نویس

- API فعلی در [`API.md`](./API.md) مستند شده است. مهاجرت فهرست پروژه‌های موجود در `localStorage`، حذف پروژه/ستون و نسخه‌بندی migrationهای SQLite در محدوده‌ی این مرحله نیستند.
- این مدل برای احراز هویت چندکاربره یا محیط تولید طراحی نشده است.
- جدول‌ها هنگام نخستین درخواست API ساخته می‌شوند و داده‌ی نمایشی فقط برای پایگاه‌داده‌ی تازه مقداردهی می‌شود. در این مرحله ابزار versioned migration اضافه نشده است.

## تصمیم‌های تأییدشده

کاربر این طرح را تأیید کرده است: پروژه یک تخته دارد، تخته‌ی جدید پنج ستون خالی می‌گیرد، ترتیب و حدود طول متن طبق پیشنهاد است و کاربر فقط شناسه/نام کاربری دارد. جابه‌جایی درون‌ستونی نیز اکنون در فرانت‌اند پیاده شده و در ستون `position` مدل ذخیره خواهد شد.
